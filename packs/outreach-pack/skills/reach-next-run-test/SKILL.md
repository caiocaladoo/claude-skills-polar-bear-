# Next Run Test

## When To Use
You keep changing five things at once and learn nothing. The review gave you one candidate change. This answers: how do I try it so that, a few runs from now, I can say whether it was worth keeping?

## When Not To Use
If you have not reviewed your own counts yet, run Outreach Review first; a test with no starting point proves nothing. This is not a statistical test, and with small runs it never will be: it is a disciplined way to change one thing.

## Inputs
- The one change from your Outreach Review.
- Your counts so far for the thing you will compare against.
- How many runs you are willing to wait before looking.
If you have none of this, I start from the change you describe in one line and mark the plan as a first draft with no starting count.

## Approach
One change at a time: plan it, run it, look at what happened, decide. This improvement cycle is widely taught and is described here generically. The discipline is in writing the expectation and the keep-or-drop rule before the runs, because afterwards any result can be explained. With about ten people a run, one run tells you almost nothing, so the plan says how many runs you wait. The failure it prevents: a new subject line, a new reason and a new channel in the same week, and no idea which one mattered.

## Workflow
1. Ask at most three questions: the one change, what you expect it to do and why, and how many runs you will wait.
2. Write the change as one sentence about your own action: "I will [do this] where I used to [do that]". If it takes two sentences, it is two changes; pick one.
3. Write the expectation and the reasoning before any run, in your words. This is the line you will read back later.
4. Say what you will count, from columns already in your Outreach Log, and what the count was before. Nothing new is tracked about the people.
5. List what stays the same during the test: who you choose, the channel, the run size, the warm-first order.
6. Set the look date as a number of runs, not a result. You do not peek and stop on a good week.
7. Write the rule in advance: what would make you keep the change, what would make you drop it, and what counts as "cannot tell", which with small numbers is the likely answer and still a result.

## Output Format
```markdown
# Next Run Test
The change: I will [do this] where I used to [do that] | Starts with run: [number] | Look after: [number] runs
## What I expect, written before the runs
[Your expectation, and why.]
## What I count
| Count (from the log) | Before the change | After [number] runs |
|---|---|---|
| [replies / first calls, of people written to] | [count of count] | [to fill in] |
## What stays the same
- [who you choose] · [channel] · [run size] · [warm before cold]
## Keep, drop or cannot tell
| Outcome | What would show it (set now) |
|---|---|
| Keep | [your rule] |
| Drop | [your rule] |
| Cannot tell | [your rule] |
## Decision
[Your name] runs the change for [number] runs and decides on [date] to keep it, drop it or call it "cannot tell".
```

## Done When
- The change is one sentence about your own action.
- The expectation and the keep-or-drop rule were written before the first run.
- What is counted already exists as a column in your log.
- The look date is set as a number of runs.

## Quality Bar
- One change only; a second idea waits for the next test.
- The test changes what you do, never how much you send: the run stays at about ten.
- No claim of proof: small counts support "seems worth keeping", not more.
- Nothing about the people is tracked, scored or compared.
- You choose the change and judge the result from your own counts; nothing is automated to run the test.
